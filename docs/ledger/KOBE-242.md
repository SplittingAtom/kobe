# KOBE-242: flaky tests

Evidence from CI logs (original failing attempts of #205/#203 were replaced by reruns; the e2e logs only keep the shard output and a short server log tail).

1. connector-grants audit "6789": `audits add, replace and remove without the key or its hint` searched the whole `audit_log` JSON for the bare key suffix (`KEY2.slice(-4)` = `6789`). Random UUIDs/timestamps in the table contain `6789` by chance (about 1 run in a few hundred). Now it searches for the hint form `••••6789`, which is what the server could leak.
2. share_file "Policy could not be evaluated" (run 38063763519, executor, attempt 1): the generic message is only produced by a thrown error in `decidePolicyCheck` (buildInput/approvals) or the engine's internal-error deny. Engine errors are logged, the `decidePolicyCheck` catch was silent, and no `policy engine error` line is in the log, so the throw was in the unlogged path (a read in `buildInput`, i.e. a transient DB failure). Not a missing-context race: a missing run/thread yields a specific `run_not_active` message. Fix: both steps are read-only, so retry once (150 ms) before denying, and log every failure with its cause. Still fails closed after the second failure. Unit tests in `sandbox-wire/policy-check.test.ts`.
3. gate2 "Bifrost has not restarted: got [2]" + `in_sync=false` (run 38060643247, attempt 1): Bifrost really restarted twice during startup on the loaded k3d runner (liveness `/health` has the 1 s default timeout, 3 misses kill it), so the sync could not finish within 90 s. Fix: probe `timeoutSeconds: 5` (liveness failureThreshold 6, readiness timeout 5), sync wait 180 s, and run.sh prints the restart reason and previous logs when the count is not 0. Chart test added.

Update (2nd occurrence, #199 run 38073066856 executor): same symptom, so share_file was refused by policy (tool result `policy.denied: Policy could not be evaluated`), not skipped. Both occurrences (#205: first_token_ms=5228, #199: 5447) took about 5.3 s to deny, which is `APPEND_LOCK_TIMEOUT` (5 s) plus the model turn: the approval broker's `#create` (share_file is a kobe write, so it asks for approval, which the e2e auto-approves) locks the thread then run row and hit `lock_timeout` (55P03), which `decidePolicyCheck` turned into the generic deny. The holder of the row lock was not captured (server pods restarted before Diagnostics, so their logs are gone); the circumstantial evidence is the 5 s timing, not a log line. Mitigation: `#create` rolls back fully, so it is retried (3 attempts) on 55P03; decidePolicyCheck now logs causes; run.sh prints the server's policy/lock lines when share_file hits this deny, so a third occurrence names the lock holder.
